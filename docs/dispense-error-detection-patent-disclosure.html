1 · Field of the Invention

The system relates to computer-implemented quality assurance for pharmacy operations — specifically, the automated detection of errors, discrepancies, and potential duplicate-billing (fraud/abuse) signals in drug dispense reports that have been digitized from printed or scanned documents via optical character recognition (OCR) and large-language-model (LLM) extraction.

A dispense report is a tabular pharmacy document listing, for a reporting period, each medicine dispensed (identified by name and National Drug Code, or "NDC"), and, for each prescription fill ("dispense line"), the patient, prescriber, insurance plan, quantity, days-supply, price, insurance-paid amount, and refill status. The invention automatically audits these reports and flags likely mistakes before they are committed to inventory and financial records.

2 · Background & Problem Addressed

Dispense reports arrive as printed sheets, faxes, or PDFs from disparate pharmacy management systems, each with its own column layout. When these are digitized, two independent classes of error co-exist and are hard to separate:

  1. Extraction/transcription errors — OCR and LLM extraction introduce artifacts: a drug name "bleeds" text from an adjacent column; an insurance code is truncated or gains a stray trailing digit; an NDC loses a leading zero; a numeric field is emitted as a stringified float ("30.0").
  2. Genuine dispensing / billing errors — independent of digitization: the same patient billed twice for the same drug on the same plan (duplicate claim); a discontinued NDC still being dispensed; a unit-of-use product (an inhaler, a test-strip kit) recorded as a fractional quantity; an implausible quantity-to-days-supply ratio; a priced line with zero insurance payment.
The core difficulty: a naïve rule ("same patient + same drug twice = duplicate") fires constantly on noisy extracted data, because the very fields used to group records — patient identity, insurance code, drug code — are exactly the fields corrupted by extraction. A useful detector must therefore normalize the noise away first, using domain knowledge of how these specific fields get corrupted, and only then apply the domain rules. The invention is the coupling of the two: a normalization layer purpose-built for pharmacy-report noise feeding a layered domain rule engine.

Prior manual practice requires a trained pharmacy technician to eyeball each report, cross- check codes against a drug directory by hand, and mentally reconcile totals — slow, inconsistent, and unauditable. Generic spreadsheet validation cannot reconcile against the live FDA drug directory, cannot fold insurance-code variants, and cannot group patients across rows without exposing protected health information (PHI).

3 · Summary of the System

The system audits an extracted dispense report through a structured engine that produces a ranked validation report — a list of typed alerts, each carrying a stable machine code, a severity, a precise location (which medicine row / which dispense line), and a human-readable remediation suggestion. Distinguishing characteristics:

  • A two-tier evaluation split by data dependency. Tier 1 checks are pure-data (no network) and run the instant extraction finishes, inline in the ingestion worker. Tier 2 checks require an authoritative external lookup (the FDA Drug NDC Directory) and are deferred to interactive validate/save calls so per-code network latency never stalls ingestion.
  • Privacy-preserving cross-row grouping. Records are grouped by a salt-free de-identified patient key — a truncated hash of normalized name + phone digits + ZIP5 — so the same physical patient is recognized across rows without any raw PHI ever entering an alert payload, a log line, or an external lookup.
  • Noise-aware canonicalization. Insurance codes are folded through a synonym map plus column-bleed digit-stripping; 11-digit NDCs are expanded into the multiple hyphenated 10-digit candidate forms the FDA directory actually indexes.
  • Cached authoritative reconciliation. FDA lookups (including negative results) are cached per-NDC with a time-to-live, so a directory that is slow and rate-limited can back a low-latency interactive experience.
  • A severity taxonomy that gates persistence. Alerts are classed ERROR / WARNING / INFO / INDETERMINATE / PASS; any ERROR makes the report blocking and refuses the database write unless an authorized operator explicitly force-saves, which is recorded with a full audit trail of the errors overridden.

4 · End-to-End Pipeline Architecture

Detection is one stage of a larger asynchronous document pipeline. Understanding where it sits explains the two-tier design.

   ┌────────────┐   scanned / PDF dispense report
   │   Client   │─────────────┐
   └────────────┘             ▼
                     ┌───────────────────┐
                     │  Upload endpoint  │  store bytes, enqueue job (Kafka)
                     └─────────┬─────────┘
                               ▼
                     ┌───────────────────┐
                     │  Dispense worker  │  (a) OCR + LLM extraction → report JSON
                     │                   │  (b) TIER-1 validation  (pure-data, inline)
                     └─────────┬─────────┘
                               ▼   report JSON + embedded Tier-1 alerts
                     ┌───────────────────┐
                     │  Operator UI      │  edits fields; on each edit calls…
                     └─────────┬─────────┘
                               ▼
                 POST /dispenses/validate     ← TIER-1 + TIER-2 (FDA), no write
                               │
                               ▼
                 POST /dispenses              ← re-validate, then GATE:
                                                any ERROR ⇒ 422 (block) unless force_save;
                                                else persist + decrement inventory

4.1 Why the tiers are split

Technical rationale. Tier-1 (services/validation/tier1.py) touches nothing but the extracted dictionary, so it runs synchronously inside the extraction worker and the operator sees structural alerts the moment the document is parsed. Tier-2 (tier2.py) issues one FDA directory lookup per distinct NDC (~1–2 s each on a cache miss); running it inside the worker would risk exceeding the pipeline's result timeout, so it is deferred to the interactive validate/save endpoints where a per-NDC cache makes repeat calls sub-millisecond.

The two entry points:

validate_tier1(report_data)                       → ValidationReport   (no I/O)
validate_tier2(session, report_data, tier1=...)   → ValidationReport   (+ FDA modules A/B/C)

Both return the same strict ValidationReport object: a summary (error/warning/ info counts + a blocking flag), the ordered alert list, a recomputed grand-total block, and a per-patient rollup.

5 · Foundational Normalization Primitives

These are the enabling "technical logic." Each exists specifically because a downstream domain rule would misfire on raw extracted data without it. They are the reason the domain rules are reliable rather than noisy.

5.1 De-identified patient key (cross-row grouping without PHI)

To decide whether two dispense lines belong to the same physical patient, the engine derives a stable key from three weakly-identifying fields, deliberately excluding any raw identifier from the output:

patient_key = sha1( normalize(name) + "|" + digits(phone) + "|" + zip5(address) )[:16]

  normalize(name) : uppercase, collapse internal whitespace, trim
  digits(phone)   : keep digits only  →  "(347) 555-0199" → "3475550199"
  zip5(address)   : first 5-digit ZIP found in the address string
Why hashed & truncated. The same 16-hex key groups a patient's lines across the whole report, but the key itself is non-reversible and carries no name, phone, or address — so it is safe to place in alert payloads, logs, and the persisted record. A separate light-touch display label ("CEDENO, B.") is generated only for the operator UI, never the machine key.

5.2 Insurance-code canonicalization (synonym folding + column-bleed repair)

Insurance codes print in wrapping and variant forms across pharmacy systems; the same plan can appear as several strings, and OCR frequently appends a stray digit that bled in from the adjacent column. A canonicalizer folds these to one key so duplicate-billing detection compares plans correctly:

canonical_insurance(code):
    cleaned = upper(collapse_ws(code))
    if cleaned in SYNONYMS:        return SYNONYMS[cleaned]     # EMPIREBCBS → EMPIRE_BCBS
    head = first_token(cleaned)                                 # strip bled-in trailing token
    if head in SYNONYMS:           return SYNONYMS[head]        # "MMS2084 7" → MEDICAID_MMS208
    return cleaned                                              # unknown → pass through

The synonym map encodes real observed families — Empire BCBS, Anthem, Aetna, Express Scripts, New-York Medicaid MMS codes, Advantage plans. The raw code is always preserved alongside the canonical key so a human reviewer can audit the fold.

5.3 NDC normalization (11-digit → hyphenated 10-digit candidates)

Dispense systems store NDCs as a flat 11 digits, but the FDA directory indexes the 10-digit package NDC in one of three segment layouts (4-4-2, 5-3-2, 5-4-1). Which layout applies is not knowable a priori, so the engine generates every plausible candidate by stripping the leading zero of the matching segment and queries them in order until one hits:

11-digit  00071015527
          ├─ seg0 leading 0 → 4-4-2   0071-0155-27
          ├─ seg1 leading 0 → 5-3-2   00071-155-27
          ├─ seg2 leading 0 → 5-4-1   00071-0155-7
          └─ raw 5-4-2 fallback       00071-0155-27

5.4 Cached, negative-caching authoritative lookup

Each distinct NDC is reconciled against the FDA Drug NDC Directory at most once per TTL window (default 7 days). The projected result — brand/generic name, dosage form, marketing start/end dates, package description, and a derived is_unit_of_use flag — is upserted into a cache table.

Negative caching is deliberate. A "not found in FDA" result is cached too. Roughly 5% of dispensed items are medical devices or supplies that live in a different FDA database; caching their absence stops the engine from re-hitting a slow external API on every revalidation for items it will never find.

5.5 Derived unit-of-use flag

Whether a product must be dispensed in whole packages (an inhaler, a metered aerosol, a prefilled pen, a test-strip/lancet/sensor kit) is derived from the FDA dosage-form and package-description text via a narrow keyword set, and stored as a boolean so the fractional- quantity rule (Module C) reads a flag rather than re-parsing strings.

6 · The Detection Modules

These encode the pharmacy-domain "business logic." Each module emits typed alerts. Modules that need no external data are Tier-1; modules A/B/C reconcile against the FDA directory and are Tier-2.

6.1 Field-sanity checks (Tier-1) — catching extraction corruption

CodeSeverityRule & rationale
MALFORMED_NDCERROR NDC is not exactly 11 digits. A bad NDC poisons every downstream FDA and duplicate check.
DRUG_NAME_BLEEDERROR Drug name contains column-label text from adjacent fields ("Pres Addr", "Ins Paid", "Qty Ord"…) or exceeds 80 chars — a signature OCR/parse artifact.
DUPLICATE_NDC_IN_REPORTERROR The same valid NDC appears as two+ separate medicine rows; they must be merged so per-drug totals are correct.
MEDICINE_NO_DISPENSESWARNING A medicine row has no dispense lines attached — likely a truncated parse.

6.2 Module D — quantity / days-supply plausibility (Tier-1)

Business rule. Days-supply must be positive; and the ratio of dispensed quantity to days-supply must fall inside a generically plausible band. A ratio far outside the band signals a transcription error or an implausible fill.
days_supply ≤ 0  or missing          → ERROR   DAYS_SUPPLY_INVALID
rate = qty_disp / days_supply
rate > 50.0  or  rate < 0.05         → WARNING DAYS_SUPPLY_RATE_OUT_OF_BOUNDS

Bounds are configurable (defaults shown). The band is intentionally wide — it flags gross outliers, not clinical dosing.

6.3 Modules E & F — repeat-dispensing / duplicate-billing (Tier-1)

Business rule. The strongest indicator of a duplicate insurance claim is the same patient receiving the same drug on the same insurance plan more than once in a period. The engine separates the weaker and stronger signals into two graded alerts:
ModuleGrouping keyThresholdSeverityMeaning
Epatient_key + NDC≥ 2 linesWARNING Same patient, same drug — could be a legitimate refill; worth confirming.
Fpatient_key + NDC + canonical insurance≥ 2 linesERROR Same patient + drug + plan — the strongest duplicate-billing signal; blocks the save.
Why this only works with §5. Module F would be useless on raw data: the patient would not group (name spelling/whitespace variance), and the insurance plan would not group (code variants / column-bleed). It is the composite patient_key (§5.1) and canonical insurance (§5.2) that make "same patient + same plan" a reliable equality test. Both alerts list the affected rx_no values for investigation.

6.4 Module G — total reconciliation, per-patient rollup, unpaid lines (Tier-1)

  • Grand-total recompute: the engine re-sums rx-count, price, insurance-paid, and quantity from the lines and compares to the values printed on the report. Divergence emits an INFO alert instructing downstream logic to trust the recomputed figures (guards against a mis-parsed printed total).
  • Per-patient rollup: price, insurance-paid, and derived patient-responsibility are aggregated per patient_key and returned sorted by spend.
  • Unpaid line (WARNING): a line with price > 0 but insurance-paid = 0 — flagged to distinguish a genuine cash sale from an insurance rejection that was missed.

6.5 Module H — refills-remaining exhausted (Tier-1)

A line whose refills-remaining is zero emits an INFO alert — the patient will need a new prescription before the next fill. (Robust to the extractor's "0" / "0.0" float-string quirk.)

6.6 Module A — NDC validity & discontinuation (Tier-2, FDA)

ConditionSeverityCode
NDC absent from FDA Drug NDC DirectoryWARNINGNDC_NOT_FOUND
FDA marketing-end-date is in the pastERRORNDC_DISCONTINUED
Listing expires within 365 daysINFONDC_LISTING_EXPIRES_SOON
Directory lookup itself failedINDETERMINATENDC_LOOKUP_FAILED

6.7 Module B — drug-name ↔ NDC agreement (Tier-2, FDA)

Business rule. The printed drug name should describe the product the NDC actually identifies; a mismatch means either the wrong NDC or the wrong product.

Implemented as fuzzy token-overlap: the printed name and the FDA brand/generic names are tokenized (alphanumeric words > 2 chars, digits dropped); if token overlap against either FDA name is below 34%, a WARNING DRUG_NAME_MISMATCH is raised carrying both the printed and expected names. Fuzzy matching absorbs abbreviation and dosage-form noise that would break exact comparison.

6.8 Module C — unit-of-use fractional quantity (Tier-2, FDA)

Business rule. A product that dispenses only as whole packages (inhaler, pen, kit) cannot logically be dispensed in a fractional quantity.

When the derived is_unit_of_use flag (§5.5) is set and any dispense line's quantity is not a whole number, an ERROR UNIT_OF_USE_FRACTIONAL is raised. Non-unit-of-use (bulk) products are never flagged for fractional quantity.

7 · Severity Taxonomy & the Persistence Gate

Every alert carries one of five severities. This taxonomy is what converts a heterogeneous pile of findings into a single, deterministic accept/reject decision.

SeverityMeaningEffect
ERRORMust be fixed; near-certain defect or duplicate-billing.Blocks persistence.
WARNINGProbable issue needing human confirmation.Surfaced, non-blocking.
INFOAdvisory / informational.Surfaced, non-blocking.
INDETERMINATEA check could not run (e.g. FDA unreachable).Surfaced, non-blocking.
PASSCheck ran, no issue.Silent.
The gate (blocking = errors > 0). On POST /dispenses the report is re-validated and, if any ERROR is present, the write is refused with HTTP 422 and the full alert list is returned — no inventory is decremented, no record is created. An authorized operator may set force_save: true to override; the system then persists but records force_saved = true, the overridden error count, and the full list of overridden errors on the report and each affected medicine row, and writes an audit-log entry. Detection and override are thus both fully accountable.

8 · Business-Logic × Technical-Logic Mapping

The user's framing — "a combination of business logic and technical logic" — maps directly onto the architecture. The table makes the coupling explicit: almost every domain rule depends on a purpose-built technical primitive to be reliable on OCR/LLM-extracted data. That dependency is the heart of the system.

Domain (business) ruleEnabling technical primitiveWhy the rule fails without it
Duplicate billing = same patient + drug + plan (F) De-identified patient key (§5.1) + insurance canonicalization (§5.2) Name/whitespace variance and code variants prevent equality grouping.
Repeat fill = same patient + drug (E) De-identified patient key (§5.1) Same patient printed differently would never group.
Discontinued / invalid NDC (A) NDC 11→10 candidate generation (§5.3) + cached FDA lookup (§5.4) FDA indexes hyphenated NDC10; flat 11-digit never matches; live API too slow to poll.
Wrong product for NDC (B) Fuzzy token-overlap + FDA brand/generic (§5.4) Exact string match breaks on abbreviations & dosage-form noise.
Fractional unit-of-use dispense (C) Derived is_unit_of_use flag (§5.5) Requires interpreting dosage-form/package text into a machine boolean.
Total reconciliation (G) Tolerant numeric coercion ("30.0"→30) + recompute-over-printed policy Printed totals are themselves OCR-derived and untrustworthy.
Any rule, delivered interactively Two-tier split (§4.1) + per-NDC TTL cache + PHI-free alert payloads External-lookup latency and PHI exposure would make live validation impractical.
In one sentence: the invention detects pharmacy dispensing and billing errors by first transforming noisy, OCR/LLM-extracted report fields into canonical, privacy-preserving keys and authoritative-directory-reconciled facts, and then applying a layered, severity-graded domain rule engine over those normalized facts to produce an auditable accept/reject decision.

9 · Candidate Inventive Aspects

ANALYSIS Engineering observations offered for counsel's independent legal assessment. These are not claims to novelty but observations about which aspects of the system may warrant claim consideration.

  1. The combination itself. FACT: The system couples a normalization layer (§5) specific to pharmacy-report OCR/LLM noise with a layered, severity-graded domain rule engine (§6), gating database persistence on the severity aggregation (§7). ANALYSIS: The coupling may be inventive because the normalization choices (patient key design, insurance folding, NDC expansion) are non-obvious consequences of the specific error modes in pharmacy extraction, and the domain rules (duplicate detection via patient+drug+plan) only become reliable when applied to the normalized data.
  2. Privacy-preserving cross-row patient grouping. FACT: The system recognizes the same patient across report lines via a truncated composite hash of normalized weak identifiers (name + phone + ZIP5), encoded such that no raw PHI enters alerts, logs, external lookups, or the stored record. ANALYSIS: This approach may be inventive as an alternative to deterministic de-identification (masking or removing fields) or field-based grouping (which would leak PHI). The combination of hashing, truncation, and salt-free design may satisfy novelty and non-obviousness criteria.
  3. Two-signal graded duplicate detection. FACT: The system emits two alerts for duplicate-billing scenarios: Module E (same patient + drug, severity WARNING) and Module F (same patient + drug + canonical plan, severity ERROR). The plan equality is made reliable by synonym folding plus column-bleed digit repair specific to pharmacy-report OCR. ANALYSIS: Separating the signals by confidence (advisory vs. blocking) is intuitive, but the specific repair heuristics (stripping bled-in trailing tokens, mapping observed insurance-code families) are empirically derived from real pharmacy data and are not generic to all domains.
  4. Data-dependency-driven tiering. FACT: The system partitions checks into a pure-data Tier-1 (run inline at extraction) and an external-lookup Tier-2 (deferred to interactive use), backed by per-code TTL caching including negative caching. ANALYSIS: This design is practical rather than novel in isolation, but the specific insight — that negative caching of FDA misses (for medical devices) at a 7-day TTL is necessary to avoid repeated API calls — is domain-specific and non-obvious.
  5. NDC candidate-form reconciliation. FACT: The system generates and probes multiple hyphenated 10-digit forms of a stored 11-digit NDC to match an FDA directory whose segment layout is not knowable a priori (four candidates per NDC). ANALYSIS: This is a practical solution to a real interoperability problem: pharmacy systems store flat 11-digit NDCs but the FDA indexes hyphenated 10-digit forms, and the segment boundary is not standardized. The exhaustive-candidate approach is non-obvious and may be novel in the context of automated pharmacy data processing.
  6. Severity-gated, override-audited persistence. FACT: The system derives a single blocking decision from a severity taxonomy (ERROR → blocking, WARNING/INFO/INDETERMINATE → non-blocking) and permits an authorized, fully-audited override that records the operator identity, the overridden error count, and the full list of overridden error codes on the report and affected medicine rows. ANALYSIS: The severity taxonomy itself is standard practice in quality-assurance systems, but the specific combination of (a) blocking only on ERROR, (b) forced override recording error count + codes (not just a binary flag), and (c) audit trail on affected records, may warrant consideration as a method for balancing safety with operator discretion in a regulated domain.

10 · Illustrative Example (Hypothetical Walkthrough)

NOTE: This section presents a hypothetical dispense report constructed to illustrate the system's behavior. The example is not derived from real patient data and should not be construed as a documentation of an actual claim. It is purely illustrative and serves only to walk through the logic.

Hypothetical scenario: An extracted report contains two lines recorded for a patient named "CEDENO, BRANDON":

Line 1: NDC 00071015527  "LIPITOR 10MG TAB"  rx#4410  qty 30  days 30  ins "EMPIRE"     paid $8.20
Line 2: NDC 00071015527  "LIPITOR 10MG TAB"  rx#4488  qty 30  days 30  ins "EMPIREBCBS" paid $8.20

Behavior without the system: A naïve detector might compare the two insurance codes ("EMPIRE" vs "EMPIREBCBS"), conclude they are different plans, and issue no duplicate flag. A fraud signal is missed.

Behavior with this system:

  1. Step 1 (§5.1): The patient_key is computed from name "CEDENO, BRANDON", a hypothetical phone number, and a hypothetical ZIP. Both lines yield the same 16-hex key. The patient grouping is now reliable despite formatting variance.
  2. Step 2 (§5.2): Both insurance codes are canonicalized. "EMPIRE" → "EMPIRE_BCBS" (via prefix lookup), and "EMPIREBCBS" → "EMPIRE_BCBS" (via direct lookup). Insurance plan equality is now reliable despite code variants.
  3. Step 3 (Module E, §6.3): The engine detects same patient_key + same NDC ×2 and emits a WARNING alert REPEAT_PATIENT_DRUG, listing both rx numbers (4410, 4488). This is advisory ("could be a legitimate refill").
  4. Step 4 (Module F, §6.3): The engine detects same patient_key + same NDC + same canonical_insurance ×2 and emits an ERROR alert REPEAT_PATIENT_DRUG_INSURANCE, listing both rx numbers. This is blocking.
  5. Step 5 (Tier-2, §6.6–6.8): On the interactive validate or save call: Module A confirms the NDC (00071015527) is live in the FDA Drug NDC Directory. Module B confirms that "LIPITOR" (printed) overlaps the FDA brand name (34%+ token overlap). Module C skips (a tablet is not unit-of-use). All Tier-2 checks pass.
  6. Step 6 (§7, Severity gate): The summary has errors = 1 (Module F's ERROR). Therefore blocking = true. The POST /dispenses endpoint returns HTTP 422 and writes nothing until the duplicate is resolved or explicitly force-saved with force_save: true.
  7. Step 7 (Audit trail): If the operator chooses to force-save, the system records: force_saved = true, error_count = 1, and the full list of overridden errors (Module F's code, severity, and message) on the stored DrugReport record and affected Medicine rows. An audit log entry is written with operator identity.
Key insight: The business conclusion (duplicate billing) is only reachable because two technical primitives — the de-identified patient key and the insurance canonicalizer — first transformed noisy extracted data into a canonical, grouped form. Without those normalization steps, the naïve detector's grouping logic would fail. The invention is their combination.
